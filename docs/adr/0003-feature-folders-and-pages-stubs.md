# 0003. โครงโฟลเดอร์ฟีเจอร์และสะพานถอยหลัง (Feature Folders + Pages Stubs)

* **สถานะ (Status):** ยอมรับ (Accepted)
* **วันที่บันทึก (Date):** 2026-11-03
* **ผู้มีส่วนได้ส่วนเสีย (Deciders):** ผู้ดูแลระบบ TextileOps CMMS

---

## 📌 บริบท (Context)

เพจหลักของระบบเติบโตจนแตะระดับ 100–290KB ต่อไฟล์ (เช่น `WorkOrders.jsx` 283KB,
`NeedleStock.jsx` 221KB) ทุกไฟล์กองอยู่ใน `src/pages/` เดียวกัน ส่งผลให้:

1. แก้ไขคนละจุดแต่ชนกันบ่อย เพราะขอบเขตโมดูลเป็นเพียงชื่อไฟล์ ไม่ใช่โฟลเดอร์
2. ย้ายไฟล์ = ไล่แก้ทุกจุดที่ import เสี่ยงลืมและเสี่ยงเปลี่ยนพฤติกรรมโดยไม่ตั้งใจ
3. ไม่มีกลไกใดยืนยันว่า "ย้ายแล้วพฤติกรรมเท่าเดิม 100%"

`src/pages/machines/` เป็นต้นแบบที่ดีอยู่แล้ว (Headless Hook + Tri-View)
แต่เพจอื่นยังไม่เดินตาม เพราะไม่มีสูตรย้ายที่พิสูจน์ได้ว่าปลอดภัย

---

## 🎯 การตัดสินใจ (Decision)

1. **เพจทุกหน้าย้ายเข้า `src/features/<ชื่อ>/`** (ปัจจุบันครบ 18 โฟลเดอร์
   ดูแผนผังใน `src/features/README.md`) โฟลเดอร์ `repairflow` ตั้งชื่อเลี่ยง
   `src/modules/repair/` เดิมโดยเจตนา
2. **ทิ้ง stub 5 บรรทัดไว้ที่ path เดิม** (`export { default }` + `export *`)
   เพื่อให้ route, test และ deep link เดิมทำงานต่อโดยไม่ต้องแก้สักบรรทัด
3. **ทุกการย้ายต้องมี 3 หลักฐาน:** stub-guard test (re-export 1:1),
   เทียบไฟล์ทีละบรรทัด residual-diff 0 (หักเฉพาะ prefix import),
   full suite + build เขียว
4. **ห้ามผ่าไส้ในไฟล์ยักษ์ในรอบเดียวกับการย้าย** — โครงก่อน  logic ทีหลัง
   (ดูบทเรียนในรายงาน veteran-dev: ของที่ซ่อมแล้วเปลี่ยนพฤติกรรม
   ต้องเป็นงานแยก)

---

## 📊 ผลที่ตามมา (Consequences)

### ข้อดี

- `App.jsx` ไม่ต้องแก้เลยตลอด 19 ครั้งของการย้าย — จุดเสี่ยงสูงสุดถูกตรึงไว้
- Guard 3 ชั้น (`*Stub.test`, `exportsStable.test`, `repoHygiene.test`)
  ทำให้การย้ายผิดพลาดแดงทันทีตั้งแต่ระดับไฟล์
- คนใหม่เห็นโครงโมดูลจากโฟลเดอร์ได้ทันที ไม่ต้องเดาจากชื่อไฟล์

### ข้อเสีย / สิ่งที่ยังไม่ทำ

- ไฟล์ยักษ์ยังใหญ่เท่าเดิม (ย้ายที่อยู่ ไม่ได้ลดความซับซ้อน) —
  การผ่าไส้ในต้อง grill แยกก่อน (งาน logic-scope)
- stub 19 ไฟล์เป็นหนี้ทางเทคนิคที่ต้องเก็บไว้จนกว่าทุก importer
  จะชี้ตรงเข้า `features/` (งานอนาคต, ต้องแก้ `App.jsx` = เสี่ยง route)
